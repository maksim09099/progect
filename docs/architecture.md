# Архитектура MVP «Окулус‑Фельдшер»

## 1. Цели системы

- Сократить количество очных визитов до операции.
- Снизить простои операционных слотов из-за неподготовленных пациентов.
- Стандартизировать предоперационный протокол по типу вмешательства.
- Обеспечить работу при нестабильном интернете в районах.

## 2. Контур решения

### 2.1 Frontend

- **Врач/хирург**: React + TypeScript + PWA.
- **Пациент**: облегченная веб-страница по short-code ссылке.
- **Offline-first**:
  - хранение черновиков и чек-листов в IndexedDB/localStorage;
  - очередь действий (`pending_operations`) с догрузкой при восстановлении сети;
  - визуальный индикатор синхронизации.

### 2.2 Backend

- Python (FastAPI/Django) + PostgreSQL.
- Сервисная декомпозиция (в пределах монолита MVP):
  - auth + RBAC;
  - patient-flow (карточка, маршрутизация, статусы);
  - checklist-engine (шаблоны протоколов);
  - media-service (загрузка и компрессия);
  - surgery-board (модерация хирургом);
  - notification-service (Telegram/SMS заглушка).

### 2.3 Хранилища

- PostgreSQL — транзакционные данные.
- S3-совместимое object storage — медиа/документы.
- Redis (опционально) — очередь задач, кеш статусов.

## 3. Роли и права доступа

- `DISTRICT_DOCTOR`: создание/редактирование пациента, чек-листа, загрузка файлов.
- `SURGEON`: просмотр всех районов, валидация, комментарии, подтверждение готовности, назначение даты.
- `PATIENT`: read-only доступ к этапам и напоминаниям.
- `ADMIN`: управление справочниками, аудитом и пользователями.

## 4. Статусная модель пациента

- `RED` — данных недостаточно, требуется действие врача.
- `YELLOW` — процесс подготовки идет.
- `GREEN` — подтвержден к операции, ожидает/получил дату.

Переходы:

1. Создана карточка -> `RED`.
2. Заполнен минимум протокола + загружены обязательные документы -> `YELLOW`.
3. Хирург подтвердил готовность -> `GREEN`.
4. Хирург вернул на доработку -> `RED` + комментарий.

## 5. Цифровой чек-лист

Чек-лист формируется шаблоном по типу операции:

- Факоэмульсификация.
- Антиглаукоматозная операция.
- Иные типы (расширяемый справочник).

Каждый пункт:

- `required: bool`
- `item_type: check | number | date | file | note`
- `validation_rules`
- `requires_attachment`

## 6. ИОЛ-калькулятор

Входные параметры:

- `K1`, `K2` (кератометрия)
- `ACD` (глубина передней камеры)
- `AL` (аксиальная длина)
- константы линзы (`A_const`, `a0`, `a1`, `a2`)

Выход:

- рекомендованные диоптрии по нескольким формулам;
- агрегированная рекомендация (например, медиана).

## 7. Интеграции (MVP-заглушки)

- ЕМИАС/РИАМС: адаптер с контрактом `send_referral(payload)`, `fetch_policy_status(snils, oms)`.
- Telegram bot API: адаптер `send_reminder(patient_id, text)`.

## 8. Наблюдаемость и аудит

- Лог аудита критичных действий (кто изменил статус, загрузил документ, утвердил операцию).
- Трассировка ошибок синхронизации offline-очереди.
- Метрики:
  - среднее время от создания карточки до подтверждения;
  - доля возвратов на доработку;
  - загрузка операционных дней.

## 9. Безопасность

- RBAC + JWT/Session.
- Шифрование данных «на диске» и «в канале» (TLS).
- Подготовка к 152-ФЗ: минимизация данных, журнал доступа, политика хранения.

## 10. UX-принципы

- Табличная структура, крупные шрифты, контрастные кнопки.
- Минимум экранных переходов для врача.
- Явные статусы и ошибки валидации «что именно не хватает для операции».
